# Tests

Run from the repository root with Python 3 and a C++20 compiler available as `g++`/`c++`. Native fixtures need the pinned header dependencies already in the checkout. The ESP editor check needs the documented .NET 10 SDK on PATH or in its existing tool directory (override with AV_DOTNET). Windows release builds also need the documented Wine/MSVC container and Caprica. No CI configuration is included.

```bash
python3 tests/run.py --list
python3 tests/run.py --suite unit static-data
python3 tests/run.py --suite regression integration --sanitize
python3 tests/run.py --suite performance
python3 tests/run.py --suite packaging --zip build/ArcaneVaults-NG.zip
python3 tests/run.py --suite all
```

`--test ID` narrows a selected suite. `--output results/NAME` chooses a new results directory; existing directories are rejected. The runner fails unknown suites, empty selection, crashes, timeouts and missing prerequisites. It records source hashes, commit, dirty state, child PID, commands, logs and individual exit status in `report.json`. SIGTERM to the reported runner PID terminates the active process group, including compiler children. A source change during a run invalidates its result. The local TODO is excluded from the source fingerprint.

The manifest accounts for all 17 migrated release checks, the standalone ESP-editor and shader-compiler checks, and all three benchmarks. `release` runs mandatory source suites and performance gates. Packaging runs after the candidate exists. `all` also runs diagnostic experiments, which can be expensive and require the historical Git revisions used by those experiments. Sanitizers are enabled only on checks that support them. Portable execution does not verify Skyrim ABI or engine behaviour.

## Files and results

Test sources, JSON scenarios, baseline policies and compatibility identities belong in `tests/` and are versioned. Reports, logs and measurements belong in ignored `results/`. Compiler artifacts belong in ignored `.build/`. The `build/` directory holds only the single verified ZIP and historical candidate ZIPs.

The release builder creates `build/history/<UTC-date>-<commit>[-dirty]/ArcaneVaults-NG.zip`, validates it, runs the packaging suite, then atomically copies those bytes to `build/ArcaneVaults-NG.zip`. Reports live in `results/releases/<same-id>/`. Promotion does not rename or alter the historical candidate. Failed verification preserves the previous verified ZIP. See [release-build.md](../docs/release-build.md).

## Scenario data

`fixtures/inventories/` contains version 1 physical-instance scenarios. Define symbolic base IDs, inventories, per-instance counts and metadata, actions and the expected complete inventory state. Unknown fields/references, duplicate instance IDs, invalid counts and expectations that violate quantity conservation fail before compilation.

The release build also compiles the inventory test target with MSVC and runs the expanded JSON scenarios through Wine. The portable integration suite compiles the complete production `src/InventoryStacks.cpp`, with shared engine boundary types from `support/engine.hpp`. JSON is read in C++ using the existing vendored parser. It checks owner, enchantment, favourite/worn metadata and physical quantities after partial, refused and successful moves. The fake remains a model, not the game's engine. Direct cursor checks cover chunk limits, bare remainders, duplicate/malformed counts, changed totals, disappearing entries and invalid inputs. They also cover count-only base/leveled semantics, same-total replacement and equip events, unavailable event services, expected partial removals and invalidation when a removal handler diverts another stack.

The larger Quick Transfer and loan fixtures still generate some production fragments. Their remaining extraction is documented in [COVERAGE.md](COVERAGE.md). Shared physical/UI models are separated from feature tests. Do not put transfer or classification decisions into the fake engine to make an assertion pass.

`construction-loans` checks three crafting visits with carried/banked quantities explicitly classified for construction storage, plus physical Sawn Log recovery with ownership and refused moves. This supplied classification opts out of the shipped Ignore default; `keys` checks that default retention policy and unchanged ignore-list behaviour. The experiment `construction-bulk-filter-probe` runs the storage assertions with hypothetical native bulk exclusion of non-playable items. It can fail and is excluded from release gates until that engine behaviour is established. Both write phase counts under their run's results directory; passing either model does not verify native Hearthfire crafting.

`fixtures/sorting/` holds a named item catalog and representative mixed inventories. Each physical stack declares its starting inventory, protections, metadata and explicit expected quantities per destination. `copies` expands repeated stacks with distinct identities. The catalog supplies classification masks at the engine boundary; expected destinations come from fixture data, never from the sorter. Category coverage is reconciled against `ItemCategory` and the registered vault/archive population. These labels describe representative data, while archive filtering is tested separately by the archive regression checks.

The `sorting-scenarios` integration check runs these inventories through the actual Quick Transfer controller and inspection, transfer and feedback code for the Arcane Vault menu, assigned container and hotkey handoff. It includes default settings, a protected loadout with zero moves and no inspection, same-base spares, crafting stockpiles, populated archives, 500/1,000 mixed stacks and a 1,000-stack enchanted equipment haul. Reports retain host fixture durations and work counts. Those observations are not calibrated timing gates or Skyrim measurements.

`quick_transfer_pipeline` also runs `support/transfer_startup.cpp` through all three entry paths. It checks disabled/Ignore equipment, native-worn copies, protected-item query counts, deferred initial rows and equipment markers, cancellation with stale callbacks, failed initialization and populated archives with partial/refused bulk moves. Late-readiness cases supply an external completion schedule; they do not assert that Skyrim uses that schedule or an undocumented pending flag. Conservation, owner/enchantment identity, worn/favourite protection, input restoration and one completion notification are mandatory. Work requirements reject unnecessary menu opens, refreshes before initial completion, equipped queries for protected equipment and per-base inventory rereads in a protected loadout. Readiness and work failures are retained in `startup_cases` and make the check fail. Recovery controls cover one delayed refresh, time spent waiting for the originating message box, queue setup exceptions and equipment-only capture with 1,000 unrelated inventory bases.

Use `PYTHONPATH=tests:tests/regression python3 tests/regression/check_quick_transfer_pipeline.py --startup-only --sanitize --output results/NAME.json` to run just those cases. The report names the supplied schedules, source hashes and failed requirements. Render probes remain separate; their `phase_costs` attribute declared native costs to preflight, capture, row reading, validation and archive work without changing those costs or rendering inside native calls.

The delayed-opening recovery case advances the supplied clock by 400 ms while opening the inspection menu, then leaves rows empty until an explicit recovery refresh. All three entries must still sort a spare enchanted ring and three ordinary weapons, preserve the worn ring and its metadata, and transfer two notes independently. Conservation, input restoration and one completion remain mandatory. This catches a refresh scheduled after the shared acquisition deadline; the delay is a synthetic input, not measured game latency.

Startup checks also exercise Ancient Nord swords/battle axes, ebony bows, fur/iron armor and robes with equipment categories enabled. The matrix covers bare and owned explicit stacks of one/three items, plus bare spares sharing a base with a favourited or UI-worn named enchanted copy. Each runs through all three entry paths with both equipment fields, either field alone and neither field as a conservative-retention control. Notes and ingredients must still sort. Per-item results report entry, physical shape, UI fields, validated-snapshot membership and moved/expected counts. Shape indices are bare single, explicit single, bare triple, favourite same-base spare, worn same-base spare and explicit triple. Field indices are both, equipState only, isEquipped only and neither. These cases supply classification masks and UI rows; they cannot establish native classification or menu readiness. Use `--source-ref COMMIT` to compare historical implementations with the same cases.

`quick_transfer_frames` adds a whole-interaction frame-gap requirement. It runs small and large capture, protected capture, row indexing/matching, delayed readiness, validation, candidate enumeration, job expansion, soul-gem recovery and cancellation cases through all three entries. Large scenarios use 1,000 copies or distinct bases, including both soul-gem shapes; same-base row matching uses 1,000 spares alongside a protected ring. Actual targeted production loop iterations consume 0.1 simulated ms, with draws only between fixture frames. A gap above 50 simulated ms fails even when sorting finishes correctly. Each case also requires exact destinations, conservation, owner/enchantment metadata, protected copies, restored input and the correct completion count.

The capture/validation/row prefix cases also charge every traversal step, including entries skipped while resuming a same-base list. They test bounded work and forward progress, rather than assuming skipped entries are free. These cases reject large reads that exceed the gap budget and grouped row inspection that exhausts each slice rewalking its prefix without advancing. Isolate them with `PYTHONPATH=tests:tests/regression python3 tests/regression/check_quick_transfer_frames.py --frame-phases 'capture prefix' 'validation prefix' 'row prefix' --output results/NAME.json`. An assertion failure retains partial output in an incomplete JSON report; runner stderr identifies the failing phase and inspection cursor. The frame target compiles with `-O1`, including sanitized runs; the supplied per-step costs and gap budget do not depend on host CPU time. These costs are not Skyrim measurements.

Additional scan phases cover full equipment snapshots around deposits (`transfer stack scan`), ordinary player deposits (`misc stack scan`), soul-gem stack preparation (`soul gem scan`), one carried item deposited into a populated destination (`destination count scan`), and populated-archive inventory acquisition (`archive listing scan`). The last two charge descriptor-copy loops for historical sources and scalar entry visits for the count-only implementation. They vary stored contents independently of carried loot. These are separate from the one-call opaque controls: each scan performs many charged steps before returning to its caller's deadline check. Use `--frame-phases` to isolate them. The probes charge the production traversal used by each implementation; an absent or renamed boundary fails instrumentation.

The opaque native controls pair zero cost with one indivisible 250 simulated ms call. They cover capture/validation/transfer reads, menu construction/population, UI row members, recovery refresh, menu close, item removal and the legacy bulk boundary. Each observed delay must produce the same increase against its paired frame-gap baseline. The call-specific cases require rendering before and after the call, exact transfers and retained protections. Recovery rows stay unavailable until an explicit refresh, which must run with the movie hidden. The legacy bulk call may be absent. These are blocking-exposure controls, not responsive cases or Skyrim timings. Independent uninterrupted-loop, bounded-chunk and opaque-call controls verify the probe. The released `823cd6c` fails this gate; the resumable startup and action paths must pass it. Run it with `python3 tests/run.py --suite regression --test quick_transfer_frames --sanitize`. No release build is needed to exercise it.

`inventory-preview` compiles the production preview hooks against native callback/vtable boundaries. It checks suppression of owned preview loads and rendering, callback re-registration, ordinary-menu behaviour, message revisions and restoration after cancellation. Whole-interaction frame cases also require suppression to end. The fake inventory-change view mirrors the authoritative fixture rows; its synchronization work is fixture bookkeeping, not a Skyrim timing model.

## Static installer data

The static-data suite validates duplicate JSON keys before dictionary construction, JSON syntax/types, required translations, placeholders, empty values and blank lines. It accounts for container translation keys and literal alternatives; keys without source references require an explicit retained-key reason. New dynamically assembled key families need an explicit contract before enabling them.

INI validation rejects invalid plugin/local IDs, unknown categories, empty values and duplicate/conflicting normalised identities. It preserves each file's existing formatting conventions. Package validation repeats these checks on extracted data and checks exact source bytes. `fixtures/translations.json` records format arguments; updates require review. These tests cannot prove a form exists in an installed game.

## Performance

`baselines/approved.json` pins the released reference revision and the default matrix. Gate runs compile baseline and candidate with the same current harness/toolchain. Rendering/work models run serially; loan timing variants alternate order between repeated samples. Cold/entry and return phases remain separate. On Linux the gate pins its children to one available CPU to avoid migration between cores; the report records that CPU. Raw reports record the compiler, source hashes, scenarios and samples.

Loan and equipment benchmarks retain raw elapsed time and measured fixture descriptor-mirroring time separately. Their elapsed comparison subtracts only this mirroring, which rebuilds the fake native inventory view from test rows. Initialization callbacks and production traversal remain timed. Each sample asserts the measured mirroring fits inside its raw elapsed interval.

The pipeline harness normalises historical enum spellings to current names by unchanged ordinal positions. Appended values are allowed; removed values or changed positions of shared names fail. This permits source-only renames and appended categories in baseline comparisons without runtime aliases or changing the approved reference revision.

The matrix covers zero, 100 and 1,000 additional items/quantities, distinct types, quantities and same-base physical stacks, all five stations, manual/loan modes, and Quick Transfer with populated/empty archives and protected loadouts. Existing diagnostic benchmarks retain their additional cases. No native timing claim is made from simulated call costs.

The deterministic render policy retains the 50 simulated ms limit. Work regressions fail beyond the committed relative/absolute allowance. Render probes report the initial populated archive base count; replacing bulk recovery permits three extra native calls per such base for count, removal and verification. Both sources must report the declared fixture population. This allowance does not apply to empty archives, player sorting or loan calls. Host timing fails when a median increase exceeds both the materiality floor and twice the observed sample range. A material increase within the noise range is inconclusive and also blocks verification until measured again. Inconclusive loan comparisons repeat once with the policy's eight samples; both original and repeated reports are retained, and an unresolved result still blocks promotion. The 1 ms materiality floor and 25% tolerance are fixture policies, not Skyrim latency guarantees. Samples below that resolution cannot establish an in-game speedup. A missing baseline or failed/incomplete measurement fails the gate.

Change policies explicitly with a reason and retained before/after reports. Ordinary test execution never updates expected baselines. Unit tests deliberately inject large timing/work regressions to verify failure. Actual game latency and acceptance remain in [game/README.md](game/README.md).
